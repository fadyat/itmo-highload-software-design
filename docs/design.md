# Архитектура системы контроля версий (VCS)
## 1. Общая структура и уровни

Система строится layered-архитектурой, чтобы:
* Ядро можно было использовать как библиотеку;
* Консольный интерфейс был тонкой оболочкой;
* Клиент и сервер были логически разделены.

Уровни:
- __CLI-уровень__ (Presentation Layer)
- __Application / Use Case Layer__
- __Domain Layer__ (модель системы контроля версий)
- __Infrastructure Layer__ (ФС, сеть, сериализация)
- __Server Layer__ (для удалённых репозиториев)

## 2. Представление основных сущностей
### 2.1 Файл (TrackedFile)

Файл в системе не существует сам по себе — он всегда рассматривается в контексте коммита.

TrackedFile:
* __path__ — путь в рабочем дереве
* __blobHash__ — ссылка на содержимое
* __mode__ — тип (обычный файл, исполняемый, и т.п.). Это метаданные которые говорят о том, как должен существовать файл. Например, чтобы при checkout'e файл восстановился в правильном виде

Blob (содержимое файла):
* Хранит чистые байты файла
* Идентифицируется хешем (например, SHA-256)
* Не знает ни о путях, ни о коммитах

Это позволяет:
* Переиспользовать одинаковые файлы;
* Легко получать любую версию. Так как каждая версия файла - отдельный blob с уникальным хэшем

### 2.2 Коммит (Commit)

Коммит — не снимок файловой системы, а узел в DAG.

Commit:
* hash
* author
* date
* message
* parents[] — 1 или 2 (merge)
* treeHash — ссылка на дерево файлов

Коммит не содержит файлов напрямую, только ссылку на корневое дерево.

### 2.3 Дерево (Tree)

Tree:
* отображает состояние файловой системы на момент коммита
* содержит path → (blobHash | subtreeHash)
* Позволяет эффективно хранить данные. Если каталог не менялся, у него тот же хэш

### 2.4 Ветка (Branch)

Branch:
* name
* headCommitHash

Ветка — это указатель, а не сущность с историей.

Удаление ветки = удаление ссылки (коммиты остаются, если достижимы).

### 2.5 Репозиторий (Repository)

Repository:
* список веток
* HEAD (указатель на текущую ветку или коммит)
* object storage (blobs, trees, commits)
* config (remotes, пользователь)
* индекс (staging area)
* Рабочая директория

## 3. Жизненный цикл файла

1. Файл создаётся / изменяется в рабочей директории
2. Пользователь добавляет его в индекс (add)
3. При commit:
   a. создаётся Blob (если содержимое новое)
   b. обновляются Tree-объекты
   c. создаётся Commit
4. Файл становится частью истории
5. При checkout:
   a. дерево коммита разворачивается в ФС

## 4. Получение версий
### Текущая версия
* Берётся из HEAD → commit → tree → blobs

### Предыдущая версия
* Переход к commit.parent

### Произвольная версия
* checkout по хешу коммита
* HEAD становится detached (то есть не указывающим на ветку). Режим для просмотра, новые коммиты от этого HEAD не принадлежат ни одной из веток и при checkout'e не сохранятся

Компрессия:
* дельта-компрессия не используется (дельта-компрессия - хранение diff'ов и восстановление файлов через них)
* используется структурное переиспользование объектов
* одинаковые blobs и trees хранятся один раз

## 5. Работа с файловой системой

### FileSystemService

* чтение/запись файлов
* кроссплатформенность

Ядро системы не работает с ФС напрямую, только через интерфейс.

Это позволяет:
* легко тестировать
* менять реализацию (локальная ФС / in-memory)

## 6. Application Layer (Use Cases)

Каждая команда — отдельный сценарий:
* CommitUseCase
* CheckoutUseCase
* BranchCreateUseCase
* BranchDeleteUseCase
* MergeUseCase
* CloneUseCase
* FetchUseCase
* PullUseCase
* PushUseCase
* LogUseCase

Use Case:
* принимает DTO от CLI
* использует Domain-модель
* не знает о консоли

## 7. Merge и конфликты
### Merge
1. Находится LCA (lowest common ancestor) двух коммитов
2. Выполняется слияние:
  * base (общий предок)
  * current (текущая ветка)
  * target (ветка, которую вливаем
3. Для каждого файла:
* авто-merge
* или конфликт

### Конфликт
* файл помечается как конфликтный
* в рабочей директории создаётся файл с маркерами:
```
<<<<<<< CURRENT
=======
>>>>>>> TARGET
```
* merge не завершается до ручного разрешения

## 8. Работа с пользователем (CLI)
### CLI слой:
* парсит аргументы
* валидирует формат
* вызывает соответствующий Use Case

CLI не содержит логики контроля версий.

Пример:

```
vcs commit -m "Initial commit"
```

-> CommitUseCase.execute()

## 9. Удалённые репозитории
### RemoteRepository
* name
* url
* refs (ветки, теги) - читаемые имена для хэшей коммитов

### Клиентская часть
* работает через RemoteTransport
* протокол: HTTP + JSON
* операции:
  * upload objects
  * download objects
  * sync refs

### clone
* создаёт пустой локальный репозиторий
* скачивает все refs и объекты

### fetch / pull
* fetch: только обновление refs
* pull: fetch + merge

### push
* отправка новых объектов
* обновление refs на сервере

## 10. Серверная архитектура
### Сервер VCS
Компоненты:
* API Layer (HTTP)
* Repository Service
* Object Storage
* Auth (опционально)

### Сервер
* не знает о рабочей директории
* работает только с объектами и refs
* проверяет fast-forward / force push

## 11. Использование как библиотеки
Ядро системы:
* не зависит от CLI
* не зависит от сети
* использует интерфейсы (FS, Transport)
CLI и сервер — надстройки над ядром.

## 12. Итоговая идея
* Коммиты — DAG
* Ветки — ссылки
* Файлы — blobs
* История — неизменяемая
* CLI — оболочка
* Ядро — библиотека
* Сервер — хранилище объектов и ссылок
